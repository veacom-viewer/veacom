# Contributing

Use `feature/*` or `fix/*` branches and one pull request per migration item. Keep commits small. Explain the problem, changed behaviour, commands run, and results. Every interface change shows before and after screenshots in the PR summary, plus a screen recording when it involves motion, timing or a flow of more than one step. It also follows the [design guidelines](docs/design-guidelines.md).

## Verify a change

Use the Node version in `.nvmrc` and the toolchain in `rust-toolchain.toml`.

```sh
pnpm install --frozen-lockfile
pnpm run setup:runtime
pnpm run build:core
cargo test --release --locked --manifest-path native/Cargo.toml
tools/verify.sh /path/to/studies/ct-small /path/to/evidence
```

The verification command stops on any failed check and runs desktop checks in sequence. It includes unit tests, build, video export, click budgets, import, recovery, security, interface, both GPU compilation paths, GPU startup, hardware-rendering status, and the PNG export golden. Use the exact synthetic `ct-small` recorded in `tests/golden/ct-small.json`; the export check rejects different input bytes. Until the Phase 3 fixture port, that study is generated by `bench/studies.py` in the old repository.

The renderer uses React Compiler for memoization. CI and local verification run `node tools/check-react-memo.mjs` to reject uses of React’s `useCallback`, `useMemo`, and `memo`.

Unit tests (`pnpm test`) run on Node's own test runner: `node:test` and `node:assert/strict`, with `tests/support.ts` for the few helpers assert lacks (`assertClose`, `assertFields`, `waitFor`, `stubGlobal`). Run some of them with `node --import ./tests/setup.ts --test tests/geometry.test.ts`. Node runs the TypeScript by stripping its types, so `src/` and `tests/` use only erasable syntax: no enums, namespaces or constructor parameter properties (`tsconfig.json` sets `erasableSyntaxOnly`).

CI runs on Linux for each PR and push to `main`. The macOS desktop smoke workflow is manual and reserved for release candidates. It uses a separate small Node-generated study, not the performance/export fixture. Renderer, engine, packaging, and window-chrome changes also need Windows evidence. Label the PR `windows` to run `.github/workflows/windows.yml`, which builds, tests, packages and installs the app on a GitHub-hosted runner without a GPU and runs the desktop checks that need none. It runs once when the label is added; to test a later push, remove the label and add it again. Renderer and window-chrome changes also need the Tesla T4 checks on a Windows VM, run with `tools/windows-vm/vm.sh`, which reads the VM's name and SSH files from a settings file outside the repository. Keep the VM's stop deadline, budget record, and cleanup instructions in `tools/windows-vm/README.md`, which also lists what neither covers.

Run `cargo fmt --check --manifest-path native/Cargo.toml` and `cargo clippy --release --locked --manifest-path native/Cargo.toml -- -D warnings`. Existing Rust formatting and warning failures are advisory in CI until [the dedicated cleanup](https://github.com/veacom-viewer/veacom-private/issues/7). New Rust work should not add warnings.

CI's `desktop` job runs the desktop checks on Linux for every PR, without a GPU: desktop smoke and the software-drawing notice, interface, file drop, security boundary, GPU startup, the renderer pixel suite and the video encoder. The app draws there in software on Mesa llvmpipe, which a development run on Linux uses only when `VEACOM_SOFTWARE_GL=llvmpipe` is set. A PR that changes the interface updates these tools in the same PR.

## Contributor licence agreement

Under the [draft contributor agreement](CLA.md), you keep your copyright. The maintainers promise to publish the source of each release of the public edition under GPL-3.0-or-later. You also allow them to use your contribution in a separate closed edition sold to hospitals and to keep changes made for that edition private. A buyer taking over the project gets the same rights and must accept the public-edition promise in writing.

Once the agreement is adopted, follow its “How to agree” section before merging a contribution. Check that every contributor is covered, that any employer authorisation covers the proposed terms, and that third-party material has a suitable licence. Record acceptance against the exact agreement revision. Keep signatures and employer records private.

## Review and merge

Claude reviews each PR for imaging correctness, security boundaries, data/privacy, accessibility, UI consistency, and meaningful tests. Provide a GitHub review or a review file with the checked commit and ranked findings.

Changes to `main` go through a pull request. All merges require resolved conversations and passing web, engine, desktop and secret checks. Repository admins may merge a PR without an approving review. Other maintainers need one approval, and new commits dismiss stale approvals. Squash merge after local verification and any required Windows checks pass.

## Synthetic fixtures and golden images

Never put patient data in code, fixtures, screenshots, logs, artifacts, or issues. Generate fixtures outside the source tree with fixed identifiers and deterministic pixel data. Record the generator version, dimensions, transfer syntax, and SHA-256 values in a manifest. The small CI study can be generated with:

```sh
node tools/fixtures/make-smoke-study.mjs /path/to/new/smoke-study
```

The committed export was captured on Apple Silicon (M4 Pro, ANGLE Metal). `tools/capture-export.cjs` records the actual renderer in `export/renderer.json`. On another GPU, investigate differences against a known-good build on that GPU. A mismatch still fails the gate.

Do not overwrite the export golden just to make a test pass. Capture the approved previous build with `tools/capture-export.cjs`, compare it with the proposed build, and have Claude review the reason, pixel diff, input fingerprint, and screenshots. Commit any intentional new PNG together with its provenance JSON. A changed pixel, size, or input fingerprint fails the gate; there are no excluded image regions. Unexpected PNG metadata or appended data also fails. Patient data is never allowed. An intentional colour-profile change needs a reviewed update to the export contract.

Keep independent engine checks in the old repository running until their Node replacements agree on the same build and fixtures. No Python files may be added here.

## Releases and secrets

Signing, publishing, and telemetry in release builds require Ali's approval. Release only to this repository. Use `v<version>` tags and mark beta versions as prereleases. Do not change the build identity, source license, keyboard conventions, or splash notice without the corresponding owner decision.

Keep endpoint configuration and credentials out of Git. Use GitHub Secrets or Google Secret Manager. Report security concerns privately as described in `SECURITY.md`.

## Dependency updates

Use the pinned pnpm version and commit `pnpm-lock.yaml`. electron-builder has its own install and lockfile in `packaging/`, so the root install on laptops and in Linux CI never fetches it; only packaging runs `pnpm --dir packaging install --frozen-lockfile`. Keep its `packageManager` equal to the root's. Review major upgrades one at a time; run a frozen install, the relevant tests, and the combined viewer checks. Test runtime, renderer, or packaging changes on Windows as well as macOS. Remove unused runtime dependencies. Keep Dependabot alerts open until a tested fix or a documented assessment addresses them.
