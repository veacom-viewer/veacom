# Desktop imaging boundary

On supported local Linux filesystems, the engine uses file identity and change times for settled files after a short read lease confirms there is no existing writer or writable mapping. It checks the open file before and after every read. On APFS it reads a private copy-on-write clone made at import and also checks the original file's identity. A file of at most 256 KiB skips the clone and is checked by its fingerprint instead (below), which costs less than a clone for each small slice. Writes through a mapping can leave timestamps unchanged. The clone keeps those writes out of previously imported images and exports. Its temporary directory uses the same permissions and crash cleanup as archive extraction.

Elsewhere (recently written files, Windows, other filesystems and the browser build) import reads only a file's first 8 KiB of headers and records its fingerprint: its size and modification time, and on Unix and Windows its identity and change time, which a copy over the file moves even when it keeps the copied file's modification time. Every later read checks the fingerprint before and after it, and a file whose fingerprint changed is refused as changed since import. Import also keeps a SHA-256 of those first 8 KiB, and every later opening reads them again and compares: on Windows a copy over the file can keep every time the system reports, but not the patient, study and image identity in its headers. Nothing reads a whole file to import it, so the first image does not wait for the study to be read. What this does not catch is pixel data past the first 8 KiB replaced with the size, the headers and the times kept, or written through a mapping made before import. In the browser the page's File objects have no time to check, and the browser itself refuses to read a chosen file whose file on disk has changed.

Electron's main process starts the engine with its stdin and stdout as pipes, and only main holds their other ends. The engine opens no port and has no token: no web page, and no other program on the computer, has anything to connect to. The sandboxed renderer receives typed operations and one-use read capabilities, not a way to reach the engine or an arbitrary proxy.

- Native Open dialogs, the import window and CLI startup selections create opaque import capabilities in main. A later launch (Explorer's **Open with VEAcom** while VEAcom runs) sends its own arguments with the single-instance request; main reads the paths from them and authorizes them the same way, and the page only learns that there is something to take. OS-backed browser File objects are resolved inside the isolated preload; it sends their native paths directly to main and returns only capabilities to the page. Synthetic Files without OS backing are rejected.
- The import window (`src/import-window`, `electron/import-view.cjs`) is not part of the page. It is a separate view laid over the application window, at its own origin (`veacom://import`), in its own session (`persist:veacom-import`, so its storage is apart from the page's, in development too) and with its own preload (`electron/import-preload.cjs`). Its code is first-party only, with no packages: `tests/import-window.test.ts` checks its sources and the build fails if its chunks hold anything from outside `src/` (`vite.config.ts`), so a compromised dependency of the application cannot drive it either. The page can only ask main to open it (`openImportWindow`), within 1.5 s of the user's own click or key press in the application window (Electron's `input-event`, which page JavaScript cannot make), and receives capabilities for what the user opened there, or none. The disc button's request also says what to open, though not where: where the system tells which drives hold a disc (Windows) and exactly one does, main opens that disc with no window, but only within 1.5 s of a press of the mouse or a touch in the application window. After a key press the window is shown at the disc's drive instead, since a reader holds keys down to page through images far more often than they click. The page names no path there either, and with several discs the window is shown. Open ignores clicks for half a second after the window appears, so a click the page timed to land there is not taken. Main serves the folder browser (`electron/file-browser.cjs`) only to that view's own main frame. The browser refuses network and device paths (`\\server\share`, `\\?\`, `\\.\`, `/net` on macOS) before anything is opened, unless they lie inside the home, Desktop, Downloads or Documents folder, which Windows can keep on a server. On Windows the drives' kinds and names come from the engine (`drives`, `native/src/drives.rs`): it opens nothing on a drive, and reads a volume's name only for a drive main has just reached. Main takes from its answer a letter, one of four kinds and a name of bounded length.
- The engine checks the signature before allocating for a PNG, JPEG or BMP. For files over 64 KiB, indexing tries the first 64 KiB and sends the full file only if the decoder needs a longer header. Concurrent reads share 16 MiB of encoded input. A larger input uses the allowance alone, up to 256 MiB. The engine holds this allowance until the desktop decoder replies or its deadline expires.
- Electron sends pictures to sandboxed renderers with a blank page, a private in-memory session, and a first-party preload. The session denies requests and permissions. The preload reads encoded pixel dimensions before allocating a bitmap. JPEG print density does not change those dimensions. EXIF orientation can swap the displayed axes. Main checks the reply, and the engine enforces 32,768 pixels per side at import and 64 million RGB samples per frame at decode. Imports containing DICOM skip picture headers. A stalled renderer is replaced, including during startup.
- VEAcom decodes nothing of RAR, and opens a RAR archive on Windows alone. It first walks the archive's own headers, which are plain (`native/src/rar_headers.rs`): the file has to start as a RAR archive, reach its end header, be no part of a set and hide no headers. The reader takes every format it knows, among them a list of this computer's files for it to read, and it takes an archive cut between two files for a shorter one; neither reaches it. Then the engine starts the system's own archive reader (bsdtar: `tar.exe` in the Windows system folder), by its full path, with the archive as its standard input, pipes as its output, an almost empty environment, the system folder as its working folder, and no console or window (`native/src/system_archive.rs`). The reader is given no file name and no folder, so nothing in an archive can tell it where to write. It answers with the archive's files as a tar stream, and the engine checks every name and size in that stream as it does a ZIP entry's before it writes a file itself, into the same kind of private extraction folder: no name that leaves the folder or that Windows reads specially, no link, at most 50,000 files, 2 GiB a file and 8 GiB in all. Each file it wrote is then compared, in order, with the CRC-32 the archive's header gives for it: the reader hands over a stored file whose bytes have changed without a word (libarchive 3.8), and an import whose files are not the ones the headers list fails. A file that starts as a RAR archive and is also laid out as another format the reader knows may still be read as that format, by that format's code; the stream's checks and this comparison apply all the same. The reader's restrictions are in place before its first instruction (`native/src/archive_reader_windows.rs`): Windows creates it suspended and already inside its job, whose limits are set before the reader exists, and the engine lets its first thread run only once Windows says the reader is in that job. The job ends the reader with the engine, lets it start no other program, bounds its memory at 1 GiB, and keeps it from other programs' windows, the clipboard, other desktops, the computer's settings and logging off. Its token is the user's, restricted: Windows checks each access a second time against the Users group, everyone, a SID made for that reader alone and the logon session, which the user's own folders, the user's registry and the import's private extraction folders do not let in. It holds no privilege but bypassing traverse checking, and runs at low integrity, so it can write nowhere the user can and cannot open the user's other programs. It inherits the three handles it is given and no other. A cancelled import ends the reader, also one that has stopped answering. What the reader can still read is what the Users group or everyone may read: Windows' own files, removable drives and discs, and folders that let the Users group in, as a new drive's do by default. Neither the job nor the token separates it from the desktop it runs on or from the network. macOS and Linux start no reader restricted from its first instruction here: they refuse RAR and ask for the extracted folder, as the browser build does.
- Imports consume valid capabilities once. Renderer-supplied filesystem paths are rejected. Selection capabilities expire after ten minutes.
- Frame/volume requests identify an already opened series, engine generation and optional frame index. Main validates them and creates a one-use `veacom://app/_imaging/{frame|volume}/{nonce}` URL. This protocol branch streams only the registered engine read (that frame or volume), retaining cancellation and the three source-frame identity headers. It avoids an extra whole-volume structured-clone copy through IPC. Pixel capabilities expire after one minute.
- DICOM/media export destinations remain owned by native dialogs or main-created staging directories. A destination supplied by page JavaScript cannot override the selected folder. Ordinary file saves also use the native Save dialog.
- IPC handlers accept only the application window's main frame at `veacom://app` (the import window's, only its own view's main frame at `veacom://import`), or the exact explicitly configured development origin. The production CSP blocks direct loopback connections.
- The application page's content policy allows WebAssembly to compile (`'wasm-unsafe-eval'`, still no script from text), for the landmark model's runtime in a Worker (docs/landmark-model.md); the import window's does not. The page gets the model's two files only through main (`landmarks:model`), which takes a file's name from the set in `electron/landmark-model.json`, never a path or address from the page, downloads it only from the release download path and GitHub's file hosts (as updates do), checks its size and SHA-256, and keeps it in userData under its hash. The film's pixels stay in the page.
- A folder to label (docs/deformity-planning.md, "Labelling a folder") is chosen in main's own dialog (`label:open`). Main lists the DICOM files directly inside it and keeps their paths; the page gets a token, the films' names and their plan files' text, and names a film only by the token and its place in the list. `label:film` gives an import capability for that film, as Open does. `label:write` writes only `<film>.veacom-plan.json` beside that film, only text that parses as a deformity plan of at most 2 MB, only over the plan file the page was given (or none) and only if that file is itself a deformity plan, through a temporary file of its own renamed into place.
- The page reaches the system clipboard only through main: text for a report, and a picture of what it shows (Ctrl+C). The picture arrives as the pixels the page drew (opaque RGBA, at most 8192 pixels a side and 36 megapixels), never as an encoded image, so main decodes nothing a page hands it (`electron/clipboard-image.cjs`). The page draws the picture with its corner texts as they read with patient details hidden.
- The engine accepts commands only on its inherited pipes. Protocol 2 bounds each request at 16 MiB. Each work queue accepts at most 32 waiting requests and 16 MiB of queued payloads. Fixed workers keep control calls and frames available during imports. Electron admits four volumes and four frames at a time. Pixel reads grant up to 1 MiB each and share 8 MiB of credit across the connection, including 1 MiB reserved for control responses. An unread pixel stream receives no credit. The receiver checks frame size, body length and credit before accepting pixels. A broken channel retires its child through the same bounded restart policy as a crash. Closing stdin ends work after active operations finish cleanup.

Engine restart cancels outstanding broker work and revokes pixel capabilities/catalog authorization. The renderer separately checks generations and source-frame identity before accepting pixels. Development uses Electron's same broker; the old browser `core-connection.json` fallback is removed.

## Privileged test access

`VEACOM_TEST_MODE=1` enables `app.__VEACOM_PRIVILEGED_TEST__` in Electron **main**, for Playwright's privileged main-process evaluation. It grants fixture import capabilities, makes engine requests from main for native test assertions (`coreRequest`: the check receives the answer; the pipes stay in main), records imports, and can hold/release pixel requests. None of these methods are exposed by preload or renderer IPC. Normal launches do not create this object.

UI test hooks may consume granted import capabilities but cannot authorize raw paths. The helper in `tools/privileged-imaging.cjs` keeps test setup out of the page. Do not give the renderer `window.veacom.core()` or any other way to reach the engine to make a test pass.

## Validation

Focused broker/API/cache tests pass. The engine protocol tests (Rust `pipe::tests` and `protocol_tests`; `tests/engine-pipe.test.ts` and `tests/engine-process.test.ts`) cover messages split anywhere, every operation by name, an answer's window and credit, cancellation before and during an answer (a frame request cancelled while it waits is never decoded), oversized and malformed requests, a panicking request, an engine speaking another protocol at start, and stdin closing. The actual Mac desktop security check covers authorized CLI, picker and OS File imports; the import window (the page has no folder browser and cannot open it without the user's input; closing grants nothing; opening grants one-use capabilities; network paths refused; a foreign frame with its preload is refused); raw path and synthetic File denial; scoped/replay-resistant pixels; an untrusted browser frame; picker-owned export; and production CSP. Its window ignores the real mouse and keyboard (its own input comes through Playwright), so a key press from the person at the computer cannot open the import window in its place. The OS-drop check also exercises files, duplicate files, directories and internal series dragging with real disk-backed File objects.

RAR import, on Windows: `archive_reader_windows::tests` create the reader and find it, before its first instruction, in its job with the job's limits, with a restricted token at low integrity and no privilege but bypassing traverse checking; started, it hands the archive over. Asked to start a program, it is refused by its job, which reports its one process taken and has held no other; asked to read a file in a private folder of the user's, to write into one, or to write into a folder that lets everyone write, it cannot, while a file every account may read is handed over. Windows' own access check, given the reader's token, lets it into neither the user's registry nor that folder, and the engine's token into both. The engine's `system_archive::tests` read synthetic archives whose files are stored (headers and plain bytes, written by the tests themselves) through the system's reader and compare every file; they cover names that would leave the extraction folder or that Windows reads specially, links, the file, size and count limits, a protected archive, a damaged one, a stored file with a changed byte, a list of local files named `.rar`, and a tar stream cut short or with a damaged header. `rar_headers::tests` walk RAR 4 and RAR 5 headers written by the tests: every cut of an archive, every changed header byte, a part of a set, hidden headers, a file with no CRC-32 and files that are no RAR archive. `ingest::tests` compare a RAR's catalogue with its folder's, and `tools/check-engine-pipe.cjs` opens one over the real pipes. On macOS and Linux, `ingest::tests` and `tools/check-engine-pipe.cjs` check that RAR is refused with its message. Checked on Windows 11 with bsdtar 3.8.9.

These checks establish the tested process/file boundaries. They are not a claim that the entire app has undergone a security audit. The final packaged build must include the rebuilt engine as well as the broker and preload changes.
